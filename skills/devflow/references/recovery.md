# 产物完整性、损坏恢复与自检

## 完整状态表模板

仅门禁时刻使用（见主 skill「进度展示」）。**不要**在普通追问轮输出。

```markdown
---
## Workflow 状态

| 项 | 内容 |
|----|------|
| 当前步骤 | 步骤 N — \<名称\> |
| doc_root | \<路径\> |
| 本步产出 | \<文件路径列表，无则「无」\> |
| ADR | \<路径或无 — 无时写原因\> |
| 已跳过 | \<步骤 + 原因；无则「无」\> |
| 产物完整性 | \<通过 / 失败项\> |
| 编码授权 | \<待 CHECKPOINT / 已确认（阶段=步骤4）/ 不适用\> |
| 待你确认 | \<CHECKPOINT / 例外停顿；无则「无」\> |
| 下一步 | \<具体动作；步骤4 完成后用主 skill 固定提示\> |
---
```

## 两层校验（勿混）

### A. 产物完整性

读取 todolist.md 元信息，先枚举元信息指向的目录，再按当前阶段逐项验证磁盘证据。在完整状态表写「产物完整性：通过」或列出失败项：

```
project_root 目录存在（CONTEXT.md / todolist.md 在此，不在 doc_root）
doc_root 目录存在
doc_root 四子目录：缺则按 defaults.md 静默补建，不计入失败项
阶段≥步骤2：context 元信息指向的文件存在
阶段≥步骤3：spec 元信息指向的文件存在
阶段=步骤3且已有 tickets_root / 任务清单：tickets_root 存在且枚举到 ≥1 个 .md；两者均无则是尚未拆票的合法状态
阶段≥步骤4：tickets_root 元信息存在，且目录枚举到 ≥1 个 .md
清单标题与票标题不一致：以票文件为准更新清单；只提示，不判失败、不重新拆票
```

### B. 编码授权

编码授权只看：**todolist 已写 `<!-- 阶段: 步骤4 -->`**；它表示用户已经确认编码前 CHECKPOINT，也是跨会话恢复的唯一授权凭证。它不是产物完整性的一部分。

- 步骤3 + spec 存在 + 票 ≥1 → 产物完整、编码授权待确认，是**正常待确认态**；直接展示 CHECKPOINT。
- 步骤4 + 产物完整性通过 → 已获授权，可编码或从首张未完成票续跑。
- 阶段不是步骤4 → 禁止写业务代码，即使代码工作区已有改动。

任一产物完整性失败 → 停止编码，报告精确失败项，从最早缺失步骤修复。禁止「元信息先写、文件后补」。

## 损坏处理（todolist 与磁盘不一致）

1. 从 todolist 元信息取得路径；对 spec / tickets **先枚举后读取**，禁止猜文件名。
2. 跑产物完整性，列出缺失项；步骤3 + 票齐不是失败。
3. 元信息超前、产物缺失：找到最早缺失步骤（票缺→步骤3；spec 缺→步骤2；context 缺→步骤1），只删除该步及其后的虚假元信息，保留更早完整产物。
4. 产物超前、元信息落后（写盘后更新阶段前中断）：按 `tickets/*.md` → 步骤3待 CHECKPOINT、`specs/*.md` → 步骤3、CONTEXT → 步骤2反向推断；只补元信息，不重做产物。**最高只能推到步骤3，不能据磁盘代码或票推断用户已授权步骤4。**
5. 从推断阶段继续；展开完整状态表，「已跳过」写「上次 workflow 损坏已修复」。

## 幂等恢复约束

恢复可重复执行而不改变已完成结果：

- 不重建已存在且元信息匹配的 spec，不重写已收敛的 CONTEXT，不重复拆票。
- 除用户明确「新任务 / 从头开始」外，不重置合法 todolist，不把普通续跑当成新任务。
- 不重复询问已由 PRD / fast-track / CHECKPOINT 明确确认的内容。
- 阶段4恢复前先检查已有业务代码与测试，再从首张未完成票继续；不得覆盖已有实现。
- 不因对话开头的历史 git 快照与实时状态不同而判损坏；真相优先级为 todolist → 枚举所得磁盘产物 → 本轮实时 git 状态 → 历史快照。

## 恢复场景矩阵

| 场景 | 唯一动作 |
|------|----------|
| 无 todolist、无 doc_root | 新任务：确认 doc_root 后建初始状态，进入步骤1 |
| 无 todolist、有唯一 doc_root | 新任务：复用目录，建初始状态，进入步骤1 |
| todolist 存在但无 devflow 必需元信息 | 不覆盖；请用户先改名或明确允许替换 |
| 步骤1中断 | 继续下一项未收敛追问 |
| todolist 阶段落后、spec / 票已落盘 | 只补元信息，最高恢复到步骤3待 CHECKPOINT |
| 阶段2、context 有、spec 无 | 继续步骤2生成 spec，再串联步骤3 |
| 阶段3、spec 有、票为0 | 只补拆票，再展示 CHECKPOINT |
| 阶段3、spec 有、票≥1 | 直接展示 CHECKPOINT；不跑前置阶段、不称损坏 |
| 阶段4、票均未完成、代码未写 | 产物完整性通过后从第一票编码 |
| 阶段4、部分票已完成 | 校验已有实现，从首张未完成票继续 |
| 阶段4、全部完成，本轮无发布/归档意图 | 停住，等待发布或归档 |
| 阶段4、全部完成，本轮显式发布/归档 | 进入手动挡；含归档则先归档再提交推送 |
| 元信息指向不存在的 spec | 回到步骤2，只修 spec 及其后续 |
| tickets 目录含多份旧任务产物 | 以 todolist 清单标题/当前 spec 识别当前票；无法唯一识别才询问 |
| 用户给出同任务 PRD | 续跑当前阶段 |
| 用户给出另一任务 PRD | 展示当前状态，让用户选择续跑或新开；不覆盖 |
| 历史 git 快照与实时状态不一致 | 不判损坏；使用本轮实时状态辅助判断代码进度 |

## 自检清单

### 编码前

- [ ] 本轮为 CHECKPOINT / 产物完整性失败时已附**完整状态表**；普通追问轮仅一行进度
- [ ] doc_root 四目录已存在
- [ ] CONTEXT.md / todolist.md 在项目根，**未**误入 doc_root
- [ ] spec / tickets 均先枚举目录再读取，没有猜文件名
- [ ] 产物完整性与编码授权已分开判断并写入完整状态表
- [ ] spec 与 tickets 已落盘；todolist 任务来自票文件
- [ ] 编码前 CHECKPOINT 整包已展示且用户已确认
- [ ] 未把「步骤3 + 票齐」误判为损坏
- [ ] CONTEXT 无 API/路径等技术 HOW
- [ ] 未在 CHECKPOINT 确认前写业务代码

### 步骤4 结束后

- [ ] **未**自动 commit / push / 归档；仅在用户本轮显式要求时转手动挡
- [ ] 本轮无显式发布/归档意图时已停住并附完整状态表；提示：查看变更 → 发布（先审查再 `/devflow-publish`；加归档则先归档再推）/ 「归档」

### 发布前（步骤5–6）

- [ ] 已走步骤5：审查 skill / 自审 / 或用户跳过
- [ ] 未审查且未跳过时**未**调用 `/devflow-publish`
